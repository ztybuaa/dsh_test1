# 0003 — 面板通信走与载体无关的标准通道，不用宿主 HTTP 路由

**状态**：已接受
**日期**：2026-09-15

## 决定

插件面板（网页那半边）与服务端之间的所有通信，走 DSH **与载体无关**的标准 RPC 通道：服务端注册一个具名通道，客户端按通道名与端点名调用。**禁止**使用宿主 HTTP 路由。

## 理由

第一方 `@deepseek-ai/dsh-client-connection` 的说明（本机已发布包）明确：它**无条件**提供与载体无关的 RPC 注册表；**只有**在 `webServer` 服务存在时，才额外挂载 HTTP 的 `/api` 传输。客户端侧的物理载体由**页面全局钩子**在插件启动前选定——普通 Web 应用不设它（于是走 HTTP + WebSocket），而"拥有不同物理载体的外壳"自己设它，**插件代码不必分叉**。

桌面外壳恰恰属于后者：它**不开任何监听端口**，而是把 `/api/*` 与一条流式通道映射到自己的协议上，并向页面注入载体钩子。

因此：走标准通道的插件在两种宿主下都能工作；走宿主 HTTP 路由的插件**在桌面外壳里彻底失效**——这正是既有实现在外壳下断掉的根因（它注册了 7 条宿主 HTTP 路由，客户端用相对路径请求它们）。

## 考虑过的替代

- **宿主 HTTP 路由**：只在浏览器里能用；外壳下服务不存在，注入不成立，路由根本不注册。弃用。
- **在外壳里补一个监听端口**：需要重新引入端口归属、鉴权、CORS、暴露面这一整摊事，且与官方桌面应用的设计取向（零端口）相反。弃用。

## 后果

- 面板通信的迁移**与"原生视图"无关**，是任何宿主下都要做的一次改造。
- 客户端半边必须能读到外壳注入的载体钩子——它由外壳在插件启动前装好。
- 流式能力在两种宿主下由不同机制提供（浏览器由 WebSocket 承担，外壳由外壳自己的流式通道承担），插件不应假定其中一种。
