# 0014 — 自动适配栏宽由**外壳**做：栏一变就按页面自己报的溢出让整页刚好塞下

**状态**：已接受
**日期**：2026-09-17
**票**：[#19](https://github.com/ztybuaa/dsh_test1/issues/19)（以及它第二条评论里的 `ResizeObserver` 缺陷）

## 背景：这一票要补的是 #13 只做了一半的那半句

用户最初抱怨的原话是「能不能做到**适应侧边栏的大小**」。#13 交付的是**手动**缩放
（`−` / `100%` / `+`，ADR-0013），而用户要的是**不用他按**：栏宽一变，页面自己缩放到刚好塞得下。
参考行为是他贴的 Codex 浏览器面板截图。

三条**已经测清、本票不再重推**的事实（票面与 ADR-0013）：

1. 「跟随」那条链路是好的：拖窄侧边栏时页面会重排，面板上报的矩形与画面尺寸逐像素一致 ——
   所以本票**不是**修跟随；
2. **重排解决不了他的问题**：他看的是固定宽度排版的文档站（1200px 那种），窄栏里重排不了，
   只能被裁掉右半边；
3. **手动缩放是好的**（`tests/zoom-pixels.spec.ts` 有真窗口像素证据），缺的只是"自动"。

---

## 决定一：适配跑在**外壳**里，不跑在插件里

票面给了两个实现位置，并点名"拖动侧边栏时如果有 1 秒延迟，这个功能就是废的"。
**量出来的数字选的是外壳**：

| 触发路径 | 实测延迟 | 出处 |
|---|---|---|
| 面板 → 宿主 → 请求文件 → 外壳 150ms 轮询 → 生效 | **~1.0 秒**（`coldMs 1016` / `warmMs 1008` / `zoom-reset 1005`） | `tests/panel-toolbar.spec.ts` 每次跑都重新印一遍；ADR-0013 诚实清单 |
| 外壳自己：落点变化 → 读页面两个数 → `setZoomFactor` | **26ms**（一次跳变）/ **32ms**（拖动最后一次之后）/ **12ms**（拖回宽处） | `tests/fit-to-pane.spec.ts` 的 `RAW 跟手延迟` |

差的不是百分之几十，是**两个数量级**。而"跟手"正是这一票的全部价值 —— 一个要等一秒才反应
的自动适配，用户会自动把它当成没做。

### 这不违反"壳只做非壳不可的事"

- 外壳**本来就在做缩放**：`webContents.setZoomFactor()` 是 Electron 的 API，插件永远够不到
  （ADR-0003 明令外壳不开控制端口），所以 #13 起缩放就是外壳做的。这一票只是把"改成多少"
  也交给了它；
- 适配**只做两件事**：读页面的两个数（`documentElement.clientWidth` / `scrollWidth`），
  以及可能调一次 `setZoomFactor`。它不导航、不注入、不碰页面内容、不读身份、不驱动任何东西
  —— 与 `shell/preload.js` 顶部那句边界（"除了矩形什么都不许过境"）不冲突：**这条边界管的是
  页面能对外壳说什么**，而适配是外壳对自己持有的一块视图问了一个尺寸问题。
  外壳对那块视图 `executeJavaScript` 已经有先例（`inheritLogin` 读 localStorage）；
- 策略仍然是**独立的纯逻辑**：`shell/fit.js` 不 require electron、不碰文件系统，
  `tests/fit-rule.spec.ts` 用九个用例把它逐条钉住（不需要外壳、不需要浏览器）。

### 代价（写在诚实清单里）

外壳从此**认识页面的一点内容**：它知道"这一页有多宽"。这与 ADR-0002「外壳不驱动视图」
不冲突（读一个宽度不是驱动），但它确实让外壳多知道了一件事 —— 记在这里，而不是假装没有。

## 决定二：规则本身，以及它与票面那条建议的**三处偏离**

票面建议的是：

```
若 documentElement.scrollWidth > clientWidth:
    zoom ← 当前 zoom × (clientWidth / scrollWidth)
否则: 不动
```

这条规则的方向是对的，但**只做了一半**，而且有一个量出来的坑。实际的规则（`shell/fit.js`）：

```
C     = 这一页有多宽（CSS 像素）
溢出   = C - clientWidth
溢出 == 0            → 不动
否则                 → zoom ← clamp(zoom × clientWidth / C, 25%, 100%)
```

### 偏离一：两个方向都动

只做"溢出时缩小"会在**栏拖宽**时撒谎：1200px 的页面在 620 的栏里被适配到 0.52，栏拖回
1240 之后一步都不动 —— 页面塞得下，但只占半栏，而票面第 2 条验收要的是**回到 100%**。
乘 `clientWidth/C` 本身就是对称的：内容恰好填满时是不动点，宽了就把 zoom 抬回去（封顶 100%）。

### 偏离二：`C` 不是 `scrollWidth` 本身

这一条是**量出来**的：`documentElement.scrollWidth` **不会小于视口宽度**（它就是可滚动区域）。
所以一个页面一旦塞得下，`scrollWidth == clientWidth`，**没有人再报得出它的内容宽度** ——
而"拖回宽处该回到 100%"正需要那个数。实测：夹具页在 620 的栏里、`zoom=0.5166` 时，
页面报的是 `scrollWidth = 2400 = clientWidth`（"塞得下"），于是票面那条规则永远看不到自己还有富余。

所以外壳把**每次读到的 `scrollWidth` 取最大值记着**，但**只在它真的溢出时**才记：
没溢出时那个数是视口夹出来的，把它记下来会把一个**响应式**页面记成"1226px 宽的固定布局"，
栏一窄就被当成固定宽度页一路缩小 —— 实测 `dpr` 从 1.5 掉到 0.375。
这份记忆属于**当前这份文档**（换页清空）。

### 偏离三：没有"死区"，但有一条**跟踪判定**

页面的两个宽度都是**取整过的整数**，一个 1px 的取整差会让 `ratio = clientWidth/(clientWidth+1)`。
"缩一次看看有没有变好"那种复核在**拖动时是错的**（栏宽一直在变，溢出没变小可能只是没追上）——
实测就是这么误判的：一次 20 步的拖动里页面被判"治不了"、停在了 93%，而栏早就到了 620。

现在的判据是**两份溢出样本的比较**，与"谁在动"无关：

```
样本 = {viewport: clientWidth, contentWidth: scrollWidth}   // 只在真的溢出时才有
Δ视口 = v₂ - v₁,  Δ内容 = C₂ - C₁
|Δ视口| < 8px                         → 还看不出来，不下结论（1px 的抖动不是证据）
|Δ内容 - Δ视口| ≤ min(2px, |Δ视口|/2)  → 内容跟着视口走 ⇒ 缩放治不了 ⇒ 拒绝并放回 100%
否则                                  → 内容是常数（固定宽度排版）⇒ 正常适配
```

两道门一起把关，缺一不可：

- **视口差得够多**（8px）：页面报的宽度是整数，同一页在不同缩放下 `scrollWidth` 会在 1199/1200
  之间抖（真外壳上量到过），而拖动中"视口差 1px"很常见。门槛设成 1px 时，
  `Δ视口 = 1, Δ内容 = 1` 会被判成"跟着走" —— 一个**固定宽度**页面因此被误判、缩放被放回 100%、
  这份文档不再适配。整套跑的时候正是这么红的（`RAW 拖动时的时间线: [...,0.538,1]`，
  而栏早就到了 620）；
- **容差随 Δ视口 收缩**（`min(2, |Δ视口|/2)`）：差得多的时候一点点抖动不算数，差得少的时候不比较。

判错的代价**不对称**：把固定宽度页面误判成"跟着走"，是"功能没了"；把"跟着走"的页面当成固定宽度，
是"一个完全正常的页面被缩小"。所以门槛宁可高一点。

**这条判定是"不许把本来正常的页面也缩放掉"在难例上的落地**：`width: 100vw` 配一条纵向滚动条、
`calc(100% + 40px)` 这类页面的溢出在 CSS 像素里是常数，缩得越小视口越大、内容跟着一起变大，
差永远消不掉。判定的后果是**试一次、放回 100%、此后不再碰这份文档**（并说出原因）。

### 收敛与有界（票面要求量出来）

- **一轮**最多改 `MAX_STEPS = 4` 次；
- **两次改之间等页面真的重新排版**（`waitForRelaidOut`，5ms 轮询、300ms 上限）。这一条也是
  量出来的坑：`setZoomFactor` 之后立刻读回，拿到的可能还是**旧的布局视口**，于是同一个比例
  被乘两次 ⇒ 1200px 的页面被缩到 **0.2668**（`dpr` 掉到 0.4），远小于"刚好塞下"；
- 实测收敛：固定宽度页 **两步**（改一次、确认一次）；带纵向滚动条时**三步**；
  `tests/fit-to-pane.spec.ts` 里那两行 `DSH_SHELL FIT` 就是它，`tests/fit-rule.spec.ts` 用一个
  "布局视口 = 栏宽 / zoom"的模型逐条走。

## 决定三：模式（auto / manual）由**外壳**说，面板把它**显示出来**

### 谁是主子

- **新建的空间从 `auto` 开始**：用户要的就是"不用我按 −"；
- **一个指名要某个缩放值的请求 = 接管**：面板的 `−` / `100%` / `+` 与工具里的 `zoom*`
  都走这条，外壳从此不再动这块视图的缩放（票面"手动缩放优先"那条验收）；
- **换页不变模式**。这一条是**刻意**的：换页不丢缩放是 #13 定下的语义（同源换页、换站点
  都实测过），而"换页就把控制权交回自动"与它矛盾 —— 二者只能留一个，留下的是已经在验收里
  钉住的那个；
- **回到自动是一个说得出口的动作**：面板上那颗新的 **`auto`**（RPC 动作 `desktop-view-auto`，
  请求里 `{name, mode: 'auto'}`）。没有它，手动模式就是一个**进得去出不来**的状态；
- `auto` 的动作语义是"先回 100%，再按当前栏宽适配"。先回 100% 是必需的：适配只在页面
  真的溢出时才动手，不先回 100% 的话，一个没有溢出的页面会永远停在上一页留下的那个值上。

### 读数怎么送到面板（为什么多了一个文件）

`state.json` 是**整张空间表**：发一版要列 CDP 目标、逐空间问 `cookies.get({})`，
实测一次发布 ~0.9 秒（ADR-0013 诚实清单）。而自动适配在拖动时要跟着每一帧走，
把这个代价压在拖动上等于让功能自己拖死自己。

所以分成两件事，**方向与目录都与 `state.json` 相同**（外壳写、插件读）：

| 文件 | 装什么 | 什么时候写 |
|---|---|---|
| `state.json` | 那张**表**（有哪些空间、各自在哪、缩放多少、谁在管） | 启动与每条请求之后 |
| `zoom.json` | **最新的一次缩放读数**（每块视图缩放多少、谁在管、适配跑了几轮/改了几次、这一页是不是被判过"治不了"） | 每次缩放/模式/适配变化时立刻写（几百字节，无列举、无轮询） |

两个文件里的 `zoom` 都是**读回来的** `getZoomFactor()`，所以它们不会互相矛盾：
`state.json` 里那个只是可能更旧。插件优先读 `zoom.json`，读不到就退回表里那个值
（旧外壳不写这个文件）。

面板上那句话因此有三个来源，一个都不许猜：

```
自动 78%   ← mode 来自外壳，「自动/手动」两个词来自面板自己的文案表
手动 90%
90%        ← 只有数、没有模式（旧外壳，或读不到）—— **不编**一个前缀
—          ← 连数都读不到
```

拖动时那个读数要**跟着走**：面板矩形一变就重读一次（节流 400ms，且**补最后一次**）。

### 一条量出来的竞态：在飞的那一轮会把用户刚按的值改回去

实测：面板上按 `100%` 之后，一次**已经在跑**的适配轮把它又改回 0.5167，
而模式已经是 `manual`。原因是那一轮在 `await` 读页面时被插了队。
修法是每条空间记录上一个 `zoomToken`（代次），任何"指名改缩放/交回自动"都让它 +1；
适配轮在**落笔之前**再对一次代次与模式，不对就停手并如实记一行。

## 决定四：`ResizeObserver` 那条断掉的线**接上了**（票面第二条评论）

评论里的缺陷是真的：`observer.observe()` 只在建立观察者那一刻读一次 `options.element`，
而面板是在 `useMemo` 里、**第一次渲染时**建的观察者，那一刻 `elementRef.current === null`
⇒ **它从来没有被执行过**。今天没出问题是因为那个每帧测量一次的循环把它兜住了。

修法（`shell/panel-rect.js` 的 `pointObserverAt`）：**每次测量之前**把观察者重新指向当前节点，
元素换了就 `unobserve` 旧的、`observe` 新的。于是注释与代码是同一句话，而"将来有人优化掉
那个每帧循环"也不会把跟随弄断。

三条线的分工写进了那个函数的注释，一条都不许少：

| 线 | 管什么 |
|---|---|
| `ResizeObserver` | 元素**自己的盒子**变了（拖分栏条就是这一种） |
| 窗口 `resize` | 视口变了，百分比宽度的元素跟着变 |
| 每帧测量（`tick`） | 前两条看不见的：把一个 `display: none` 的祖先打开**不会**改变元素的盒子尺寸 |

`tests/panel-observer.spec.ts`（纯 node，不需要浏览器）钉住：建观察者时元素还没挂上
（缺陷本来的形状）、第一次测量必须真的挂上去、换节点要跟过去、`stop()` 断得干净。

## 后果

- **`VIEW_ACTIONS` 多了一个 `auto`**，面板工具条多了一颗按钮。两颗枚举式断言
  （`tests/toolbar.spec.ts` 的动作表、`tests/history-truth.spec.ts` 的 DOM 顺序）跟着改了一行 ——
  这是"多了一颗按钮"的必然结果，不是行为回归。
- **`browser_view action:"state"` 报的缩放改成当场读回**（`displayState()`），
  不再报会话记忆里那个数：自动适配会在没人请求的时候改缩放，记忆会过期。
- **`−` / `+` 的起点先读回来**：从一个人为缩小过的值往上走一档，起点错了就走到错的档位上。
- **通道协议版本不动（仍是 2）**：这次加的东西都是**可选**的 —— 新插件对旧外壳缺的字段有
  兜底（读数退回表里那个值、模式缺席就只显示百分比），旧插件完全看不见 `zoom.json`。
  而 #13 那次加的是"缩放"这件能力的**存在与否**，版本号是那时候用来"对不上就明说"的；
  这次没有任何一方会因为对不上而做错事。
- **自动适配会覆盖"用户用 Ctrl+滚轮调过的缩放"**：那条路不改模式（外壳收不到那个手势），
  所以下一次几何变化/换页时适配会按栏宽重算。与 ADR-0013 那条同类代价一样，写在诚实清单里。

## 这一条没证明到的（诚实清单）

- **`width: 100vw` 配纵向滚动条那个真实页面没有量过**：量的是与它同形状的夹具页
  （`/unfixable`，`width: calc(100% + 40px)`）。判据是"内容宽度跟不跟着视口走"，两者同形，
  但真实页面的重新排版时机更多，**没有在真站点上试过**。
- **`Ctrl+滚轮` 改过的缩放会不会立刻被覆盖**：没有量过（要人手操作）。
  逻辑上它不改模式，所以下一次几何变化会重算 —— 但它**当次**不会被覆盖。
- **多显示器 / 非 1.5 dpr** 下的适配没有量过（与 ADR-0013 同一条缺口）。
- **一个从没溢出过的页面在 `auto` 模式下被留在 `<100%`** 是做不到的（规则会说"没有可适配的
  东西"），但那条状态在真实路径上取不到：`auto` 模式下缩放的每一个来源（`auto` 动作、
  换页）都先回到 100%。**没有专门测过"从一条别的路进到这个状态"**。
- **跟手延迟是在一台空闲机器上量的**（26/32/12ms）。**满载**（同时跑别的 Electron、
  或页面自己在做重活）时的数字没量过；`waitForRelaidOut` 撞上 300ms 上限时适配会停手，
  那种情形也没有构造出来过。
- **像素验收需要一块可见的桌面**（与 `zoom-pixels` 同一条限制）：无人值守/锁屏的 CI 上没试过。
- **`docs/acceptance-checklist.md` 没有更新**：它今天还写着"没有任何缩放手段"（#13 交付后
  就没改过），本票不动它 —— 那是另一件事，改一半更糟。
