# 0008 — ref 钉住快照时刻的节点,动作失败由「引擎谓词 + 中心命中测试」定性

**状态**:已接受
**日期**:2026-09-15
**关联**:ADR-0005(继承的四项决定)、ADR-0007(元素位置尺寸来源;本文件收窄了它「已知边界」的第一条)、票 T4(交互工具,issue #7)

## 背景

T3 交出的 `ref` 是「快照选择器中第 N 个匹配」:快照把每个匹配项记成 `locator.nth(i)`,动作时再在页面上重新解析一次。这在跨文档一侧有防护(文档身份 `performance.timeOrigin` 复核),但 T3 明确记下了一条**未防护**的边界:**同一文档内**列表重排或重渲染之后,第 N 个匹配会变成另一个元素,旧 `ref` 会**静默地作用在错的元素上**——既不失效,也不报错。

T4 要给动作补上可诊断的失败原因,其中「元素不存在」这一条直接撞上那条边界:只要 ref 的语义是"第 N 个匹配",就分不清"这个元素没了"和"这个位置现在是别的元素"。同时 T4 的动作面变宽(输入、悬停、下拉、拖拽、滚动),每一次误作用都是一次真实副作用。

## 决定

**一、`ref` 钉住它被读出时的那个节点。**

快照仍然由 `:visible` 选择器的匹配产生(隐藏元素规则不变),但匹配结果以 Playwright 的 element handle 固定下来,`ref` 表从 `Map<number, Locator>` 变成 `Map<number, ElementHandle>`。页面上每个元素的元数据**仍是一次求值**里读出来的:先把 handle 数组作为参数传进同一个页面函数(引擎把它解析成那些节点),再读角色/名字/状态/几何——所以 ADR-0007 的"同一次求值、同一个文档"这条没有被牺牲,只是多了**钉住**这一步。

**二、动作失败按「引擎自己的谓词 + 一次中心命中测试」定性,而不是看错误信息的第一行。**

每次按 ref 的动作都走同一条前置检查,顺序即补救顺序:

1. `ref` 不在表里 → **不存在**(文案沿用 T3,点名该 ref 与 `browser_snapshot`);
2. 文档身份不是快照那一份 → **陈旧 ref**(文案沿用 T3 的 `no longer shows`,一字不改);
3. 节点已不在文档里(`isConnected`) → **不存在**;
4. `handle.isVisible()` 为假 → **不可见**;
5. (仅指针动作)看情况滚动到视口内,然后 `document.elementFromPoint(元素中心)` 命中别人 → **被遮挡**,并把命中到的元素描述(`tag#id "名字"`)写进错误;
6. 以上都通过,动作仍然失败时,再从引擎的错误里按**证据**分诊:`… intercepts pointer events` → 被遮挡(带引擎点名的遮挡者),`Timeout Nms exceeded` → 超时(带引擎最后一句),`not attached`/`not connected` → 不存在,`is not visible` → 不可见,其余 → `failed` 并带上引擎原话。

等待(固定时长 / 选择器 / 文字)不是按 ref 的动作:它要么按时返回,要么就是**超时**,错误里点名等的是什么、等了多少毫秒、当前地址是什么。

## 理由

**为什么钉节点。** 这是把"作用在错的元素上"这类**静默错误**换成"元素不在了"这类**可报错误**的唯一低成本做法:没有发明任何新的身份体系,用的就是引擎自己的 handle;代价是每条快照多一次往返(一次 `elementHandles()`,不是每个元素一次)。反过来说,"元素不存在"这条失败原因本来就要求知道"快照列的是哪个元素",按位置解析根本给不出这个答案。

**为什么不另写一套"可见"判断。** `:visible` 与 `handle.isVisible()` 在 Playwright 内部是同一个 `isElementVisible`(`coreBundle.js` 的 `_createVisibleEngine` 与 `elementState(node, 'visible')` 都调它)。ADR-0007 要求"点击能不能落到元素上由同一个谓词决定",所以可见性判断只能来自引擎 API,不能在页面里用 `getComputedStyle` 近似一份。

**为什么"被遮挡"要自己判。** 引擎的点击会自动重试,被遮挡在它那里最终表现成**一次超时**,遮挡者只出现在重试日志里。要把它与"等不到"区分开,就必须在动作之前用与 bounds 同源的那套坐标(`document.elementFromPoint`,见 ADR-0007)问一次"这个点上最上面是谁"。

**为什么"不可见"优先于"被遮挡"。** 两者不是互斥的:隐藏元素**有时**有矩形、有时没有,而它不能被动到的原因始终是"没渲染"。先判可见性,失败原因才稳定。

## 后果

- **封住了**:同一文档内重排/重渲染后旧 `ref` 静默作用到别的元素上。`ref` 现在要么仍指向同一个节点,要么**被拒绝**。
- **封住了**:"元素不在页面里了"成为一条可报的失败原因(而不是变成"点到了下一个元素")。
- **没有封住、也不要写成封住了**:
  - **节点被移除或替换**会让 handle 变成 disconnected。这是**正确的拒绝**(报"不存在"),但它意味着 `ref` 从来不是"一直有效":跨文档失效、同文档内节点被换掉也失效。**不要在文档或错误文案里暗示"ref 一直有效"。**
  - **handle 不防导航**:它属于一个执行上下文,换文档即失效。文档身份检查仍是第一道**回答**(报错文案保持 T3 的 `no longer shows`),`load` 监听只做清理。
  - **元素完全在视口之外时不做中心命中测试**:那里没有可探测的点,而指针动作会先滚动,探测点会随之改变。此时遮挡**不由本决定判定**,退回引擎自己的重试日志(报超时,并把引擎最后一句"X intercepts pointer events"带进消息)。同文档内 DOM 变动与滚动叠加的极端情形同理。
  - **iframe 内的控件仍不进快照**(T9 的范围),所以也没有"钉住 iframe 内节点"这回事。
- **代价:handle 让节点不被回收**。一条快照最多留 `maxElements`(默认 200)个 handle;四处都显式 `dispose()`,且都走同一个 `disposeHandles()` 帮助函数:**超出上限的匹配**(快照里直接释放尾部)、**被新快照替换的旧 ref 表**、**导航**(`goto` 与 `load` 监听各一次,幂等)、**关闭会话**。`maxElements` 仍然是**输出体积**的上限,不是内存或计算量的阀(见 ADR-0007 已知边界)。释放本身没有"外部可观测"的验证方式——它不是页面行为——这一点记在 T4 报告的诚实清单里。
- `ref` 的对外语义不变:仍是快照里的数字索引,仍不让模型手写选择器(ADR-0001/0005);变化只在"这个索引解析到什么"。
