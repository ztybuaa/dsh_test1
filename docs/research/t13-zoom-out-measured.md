# T13 底稿三：缩放的「缩小」方向 —— 两条路各自的**真窗口像素**读数

> **这一份推翻了本目录里 `t13-zoom-four-roads-measured.md` 的结论（那个结论推翻过一次，这次是终局）。**
> 前两次量的都是**数字**（`innerWidth` / `scrollWidth` / `dpr` / 截图尺寸）。数字回答不了
> 用户那句"能不能适应侧边栏的大小" —— 这一份改用**真窗口的像素**，并先给量具做了自检。
> 结论：**CDP 那条路（`setViewportSize` + `setDeviceMetricsOverride`）不能把固定宽度页面塞进窄栏，
> 而且它在缩小方向上是负功能；外壳侧 `webContents.setZoomFactor()` 可以。** 产品因此只留后者。

日期 2026-09-16/17。夹具：`#bar { width: 1200px; height: 200px }`，页面最右端
（x=1150..1195，y=40..160）一块 `#ff0000` 红标；窗格矩形 `0,0,620,800`，窗口 1240×900，
屏幕 dpr 1.5。原始输出在会话工作区 `.scratch/t13-probe/{capture,grab,zf}/`（不进仓库）。

---

## 0. 先说量具：截图**不等于**用户在窗格里看到的东西

这一条是本票最贵的一课，前两次都栽在这里。

| 量具 | 它到底量的是什么 |
|---|---|
| Playwright `page.screenshot()` | **布局视口 × 屏幕 dpr** 的一张渲染图。它**不是**窗格的画面：CDP 的 `Emulation` 一旦把布局视口与窗格解耦，这张图就与窗格无关了 |
| `webContents.capturePage()` | 也**不是**窗格。实测：CDP 缩放 0.5 时它交出 **1860×2400** —— 整块 1240×1600 的模拟视口 ×1.5，比窗格的 930×1200 还大 |
| `desktopCapturer` 抓**真窗口** | **是**窗格的画面。这一份的所有结论都只用它 |

**仪器自检（量到 0 之前必须先证明量具看得见目标）**：100% 时不缩放，把页面横向滚到最右，
红标必须出现在窗口画面里。量到：

```
zoom100          : png=2400x1744  red=0       bar=461491@h422
zoom100-scrolled : png=2400x1744  red=20184@{"left":1117,"top":186,"right":1203,"bottom":417,"width":87,"height":232}
                   页面读数：scrollX=580, scrollWidth=1200, clientWidth=620
```

红标 45×120 CSS px，窗口画面是 1.9355 px/DIP（2400 px ÷ 1240 DIP）：
`45×1.9355 = 87.1`、`120×1.9355 = 232.3` —— **与包围盒精确对上**。量具有效。
`bar` 是那条 1200px 蓝条（#4a6fa5）的像素数与包围盒高度。

> 顺带一条：这也证明了 **100% 时用户够得到页面最右端**（有横向滚动条，`scrollX` 能到 580）。
> 下一节会看到，这恰恰是 CDP 的"缩小"**弄丢**的东西。

## 1. CDP 那条路：缩小**不成立**，而且比不做更糟

同一条真窗口量具，跑在**真外壳**（`shell/main.js`，`--view-size 620x800`）上，
用 Playwright 施加与当时实现**一模一样**的两步（`setViewportSize` + `setDeviceMetricsOverride`）：

| 状态 | 页面读数 | 蓝条在窗口像素里的高度 | 红标 |
|---|---|---|---|
| 基线 zoom=1 | innerWidth=620, scrollWidth=1200 | 422 px | **0** |
| zoom=0.5（先 `setViewportSize` 再发覆盖） | innerWidth=**1240**, scrollWidth=1240（"装下了"） | **422 px（一点没变）** | **0** |
| zoom=0.5（**只**发覆盖） | 同上 | **422 px（一点没变）** | **0** |
| zoom=1.94 | innerWidth=319 | 422 px（**画出来的区域**缩到 320 DIP，内容高度没变） | **0** |
| 100% 且滚到最右（自检） | scrollX=580 | 422 px | **20184** |
| **zoom=0.5 且试图滚到最右** | **scrollX 仍是 0**（scrollWidth=1240=clientWidth ⇒ 没有溢出） | 422 px | **0** |

两句话：

1. **内容一个像素都没被缩放。** 蓝条高度在四种状态下**恒为 422 px** —— 它只可能不变，
   因为窗格把模拟视口按 **1:1 的 DIP** 画出来，然后裁掉超出窗格的部分。
   `zoom=1.94` 时看得尤其清楚：画出来的区域缩到 320 DIP（右边留白 + 出现滚动条），
   而内容仍是原尺寸（不是放大）。
2. **缩小方向是负功能。** `zoom=0.5` 让 `scrollWidth(1240) <= innerWidth(1240)` 成立，
   于是**横向溢出消失** —— 用户连滚都滚不到最右端了；而 100% 时他明明还能滚过去。

> 这就是"数字全对、用户什么都没得到"的形状：`innerWidth` 变了、`scrollWidth <= innerWidth`
> 成立、**截图里也有红标**（截图覆盖整个布局视口），而窗格里一切照旧。
> `tests/view-actions.spec.ts` 里那条"最右端仍然不可见"的反证断言因此被删除：
> 它把一个只对放大方向成立、且方向本身已被否掉的结论焊进了测试。

## 2. 外壳侧那条路：`webContents.setZoomFactor()` —— 成立

同一构造（`BrowserWindow` + `WebContentsView` + `setBounds`，与外壳一致），真窗口抓图：

| zoom | 页面读数 | 蓝条包围盒 | 红标 |
|---|---|---|---|
| 1 | innerWidth=620, dpr=1.5 | 1213×**391** | 0 |
| **0.5** | innerWidth=**1240**, dpr=**0.75** | 1174×**195**（正好一半） | **5031** @ 43×117 |
| 2 | innerWidth=310, dpr=3 | 1213×**782**（放大一倍） | 0（放大时右边更看不见 —— 正确） |
| 1（重置） | 与基线逐个数字相同 | 1213×391 | 0 |

红标在 `zoom=0.5` 时的预测值：`45 CSS × 0.5 = 22.5 DIP × 1.9355 = 43.6 px`、
`120 × 0.5 = 60 DIP × 1.9355 = 116 px` —— 量到 **43×117**，精确对上。
**整页真的进了那一格，而且是按比例缩小的。**

在**真外壳**里复量（`tests/zoom-pixels.spec.ts` 的验收，走产品的完整路径）：

```
zoom100          : red=0        bar=461491@{"width":1205,"height":422}
zoom100-scrolled : red=20184@87x232   （仪器自检）
zoom50           : red=4872@{"left":1127,"top":147,"right":1168,"bottom":262,"width":42,"height":116}
                   bar@{"width":1166,"height":227}   页面：innerWidth=1240, dpr=0.75, scrollX=0
zoom100-again    : red=0        （反证：把缩放撤掉，红标回到看不见）
```

**反证成立**：同一条断言（"缩小之后最右端在窗格里看得见"）在把缩放撤掉之后必须失败，
而它确实失败了（red 回到 0）。所以这条验收不是"永远为真"的句子。

## 3. 缩放归谁：**跟视图走**（这一条是量出来的，不是选的）

Chromium 自己的页面缩放是**按站点**记的。实测（去掉外壳那次重新按上去的规矩）：

```
127.0.0.1:PORT 上设为 0.5 → 走到 localhost:PORT（另一个主机名）
  → 页面读数回到 innerWidth=620, dpr=1.5（缩放没了），而 state.json 里那个数还是 0.5（旧值）
```

所以"跟站点走"会让用户在点了一个链接之后**默默失去缩放**，而且面板上的数还会撒谎。
本票要的是"这一格能不能适应侧边栏"，所以定下的语义是 **缩放是这块视图自己的属性**：
外壳在每次主文档导航（`did-navigate`）之后把它重新按上去。实测（真外壳）：

```
同源换页（/one → /two）      : innerWidth=1240, dpr=0.75  缩放还在 ✓
换到另一个站点（localhost）    : innerWidth=1240, dpr=0.75  缩放还在 ✓
重启外壳（同一个档案目录）     : published zoom=1, innerWidth=620   缩放**不在了**
```

**语义定稿（写进 ADR-0013）**：

- 跟**视图**走，不跟站点走；跨同源、跨站点导航都保持；
- **不跨外壳重启**：新进程 = 新视图，从 100% 开始；
- 代价：用户自己用 Ctrl+滚轮调过的缩放会被下一次导航覆盖回期望值。一个属性只能有一个主子 ——
  这是"跟视图走"这条选择的必然代价，写在 ADR 的诚实清单里。

## 4. 缩放之后，那些依赖坐标的东西还成立吗

| 问题 | 量到的答案 |
|---|---|
| 快照 `bounds` 是哪种坐标 | **页面自己的 CSS 像素**。`#hit` 在 zoom=1 / 0.5 / 2 三档都是 `{x:10,y:220,width:90,height:28}`，而 `innerWidth` 分别是 620 / 1240 / 310 |
| 那"bounds 与窗格 1:1"呢 | 它一直是"bounds 与**视图 CSS 像素** 1:1"（ADR-0008 的原话）。窗格的**DIP** 尺寸在 `zoom=1` 时等于 CSS 尺寸；窗格的**物理**像素从来就不等于 bounds（本机 dpr 1.5，620 DIP = 930 物理像素） |
| 有没有流水线依赖 "bounds == 窗格物理像素" | **没有**，而且是**验**出来的：① 最可能依赖它的那条就是"按 ref 点击"（拿 bounds 决定点哪里）—— 在 zoom=1 / 0.5 / 2 三档各点一次，读**页面自己写下的效果**（`out` 变成 `t13-clicked`），三次都中；② 面板摆放用的是**面板矩形**（`DshPanelRect` 量出来的那个），不碰元素 bounds；③ 覆盖层画在页面里、用的是与 `getBoundingClientRect()` 同一套坐标（`tests/overlay.spec.ts` 已钉住） |

## 5. 截图语义：**不是**"作废"，是"换一条关系，并且这条关系在缩放≠1 时也成立"

实测（真外壳，`session.zoomTo` 之后从**磁盘上的 PNG** 量）：

| zoom | 布局视口 `innerWidth` | 页面读到的 dpr | 截图尺寸 | `innerWidth × 屏幕dpr` |
|---|---|---|---|---|
| 1 | 620 | 1.5 | 930×1200 | 930 ✓ |
| 0.5 | 1240 | 0.75 | 1860×2400 | 1860 ✓ |
| 1.25 | 496 | 1.875 | 744×960 | 744 ✓ |
| 2 | 310 | 3 | 465×600 | 465 ✓ |
| 2.5 | 248 | 3.75 | 372×480 | 372 ✓ |

**截图 = 布局视口 × 屏幕 dpr**，每一档都成立。T5 那句"截图 = 视口 × 屏幕 dpr"里那个"视口"
本来指的是**窗格**的视口；在缩放≠1 时窗格视口 ≠ 布局视口，所以要读成上面这一条。

**注意它和 CDP 那条路的差别**（这是 ADR 里必须写对的地方）：

- CDP 那条：截图尺寸 = `floor(源视口/zoom) × floor(源视口/zoom)`，**连屏幕 dpr 都不乘**
  （Playwright 的交付缩放取自它自己的 `_metricsOverride`，算出来是 1，
  `playwright-core/lib/coreBundle.js:37196`）—— zoom=2 时给 310×400，而窗格是 930×1200。
- 外壳侧这条：截图尺寸 = 布局视口 × **屏幕 dpr** —— zoom=2 时给 465×600。
  它仍然随缩放变（因为布局视口随缩放变），但它**始终是一条一致的关系**，
  而且 `devicePixelRatio`（页面读数）= `屏幕dpr × zoom` 这一条是对的。

> 上一轮本仓库写过"截图语义被有意作废"。那句话只对 CDP 那条路成立，**已随那条路一起删掉**。
> 现在文档里留下的是上面这张表 —— 与 T5 同级的一条**关系**，而不是"作废"。

## 6. 一次缩放要多久（面板 → 宿主 → 请求文件 → 外壳轮询 → 生效）

两条路都量了，**它们差一个数量级**，这是本票的一条负面读数。

**插件那一侧**（`SpaceManager.setZoom`，即 Agent 的 `browser_view` 走的路径）：外壳每 150ms
轮询一次请求文件，所以量级就是"一个轮询间隔 + 一点活"：

```
zoomTo(1)    132ms      zoomTo(0.5)  134ms / 195ms
zoomTo(1.94)  69ms      zoomTo(2)    124ms / 72ms
```

**面板那一侧**（`POST /api/desktop-view-zoom-in` → 宿主 → 同一个 `setZoom` → 读回 → 响应）：
**明显发木**，而且是**反复按也慢**，不是只有第一按：

```
zoom-in   冷: 997ms / 1118ms / 120ms      zoom-in 热(再按一档): 1026ms / 977ms
zoom-reset : 1013ms
```

即 **0.1–1.1 秒**，多数在 1 秒上下；而文件级那一条只有 0.07–0.2 秒。也就是说多出来的
约 0.8–0.9 秒花在宿主那一侧（HTTP 往返 + 外壳 `publishSpaces`：它每次都要去 CDP 端点列举
目标、并对每个空间问一次 `cookies.get({})`）。

**没有为这个数去动任何东西**：轮询间隔没改，`shell/preload.js` 那条"除矩形外什么都不许过境"
的边界一个字节没动 —— 拿一条边界去换一次按钮的响应速度，是把架构卖给一个可以单独优化的问题。
这一条如实写进 ADR 的诚实清单：**按一下缩放，画面大约 1 秒后才变**。

## 7. 这一份**没有**量到的

- **官方 Electron 桌面宿主**（不是本项目外壳 + `dsh web`）上的行为没量过。
- 缩放对**光标覆盖层**绘制位置的影响没有单独断言：覆盖层与快照同系（页面 CSS 像素），
  所以它跟着缩放走；"缩放后点击仍然命中"这条已经验了（第 4 节），但"缩放后覆盖层画在
  元素正上方"没有一条像素断言。
- `setZoomFactor` 在**多显示器 dpr 不同**的机器上的行为没量过（本机固定 1.5）。
- `zoom-pixels` 那条真窗口量具需要**一个可见的桌面**：窗口被隐藏（`windowsHide: true`）或
  被最小化时，抓图工具看不到它。本机（交互式桌面）稳定通过，**无人值守/锁屏的 CI 没试过**。
- 那 ~0.9 秒的宿主侧开销**只量了总量，没有拆开**（HTTP 往返 vs 外壳发布各占多少）。
